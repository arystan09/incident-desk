# ADR 0002: Synchronous persistence and explicit migrations

Status: proposed for owner review; F1-02 PostgreSQL execution is not yet verified.

## Decision

Use SQLAlchemy 2 synchronous sessions with psycopg 3 and PostgreSQL 17. This keeps
transaction control visible for the initial API/worker architecture. Future async
handlers must offload a complete synchronous unit of work to a thread or call a
synchronous handler; blocking database work must never run directly on the event
loop. Sessions are not shared across threads or concurrent tasks.

The caller owns an `engine_scope(Settings())`. Engine construction is lazy and
opens no connection. The scope disposes the pool on every exit path. Each
`transaction(engine)` owns a session and one transaction: commit on success,
rollback on exception (including failed flush/commit), then close. Do not commit
inside the helper or hold the scope across a provider call. No generic repository
framework is introduced. The liveness-only API does not create an engine yet.
Connect, pool checkout, and statement timeouts are bounded. Credentials use a
redacted setting; SQL parameter logging is disabled. Do not log raw URLs, settings
secret values, or driver exception details in future request handlers.

Alembic owns schema evolution. Reviewed migration operations are independent of
mutable model definitions; metadata is used for comparison/autogeneration only.
Migrations run explicitly from a checkout or container, never on API startup.
UUIDs are generated by Python callers; direct SQL clients must supply IDs.
PostgreSQL supplies initial timestamps and counter/status defaults. SQLAlchemy
updates `updated_at` for its UPDATE statements; direct SQL callers must explicitly
maintain it. There is no timestamp trigger or state-transition enforcement yet.

Foreign keys use RESTRICT, with no ORM cascade relationships. Deleting a run with
jobs/steps fails instead of silently erasing history. Direct deletion of child
records is still possible; retention/access policy is future work.

## Validation and consequences

Integration tests require an explicit TEST_DATABASE_URL for a dedicated local
LOGIN/CREATEDB role connected to the postgres maintenance database. Each test
creates a random database from template0, migrates it, closes connections, and drops
only that generated database. No application URL or pre-existing database is reset.
Tests reject remote hosts, query overrides, ordinary usernames, and non-maintenance
database names. Missing configuration/server is a failure when integration tests
are requested. Interrupted tests may leave named disposable databases for manual
inspection; cleanup never force-terminates sessions or deletes by a wildcard.

The initial downgrade drops all three tables and their data. It is only appropriate
for disposable databases. The migration test performs downgrade/upgrade only in its
newly created database. Model comparison, constraint behavior, JSONB round-trips,
and rollback tests require real PostgreSQL; offline checks cannot establish them.

See the [SQLAlchemy session documentation](https://docs.sqlalchemy.org/en/20/orm/session_basics.html)
and [Alembic commands](https://alembic.sqlalchemy.org/en/latest/api/commands.html).
